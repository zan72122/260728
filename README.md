# にじいろ ぽちゃん！しぶきラボ

4歳児向け・水飛沫が主役の3Dおもちゃ実験ラボです。Three.js で作った、
スマホ・タブレットのブラウザだけで遊べる「なげて・おとして・しぶきを見る」
おもちゃ箱です。ボタンや文字を読む必要はほとんどなく、指でつまんで、
はなすだけで遊べます。

## これは何？

飛び込み台の上でおもちゃをつかみ、プールに落とす（または投げる）と、
盛大な水しぶきが上がる——それだけのシンプルな実験ラボです。主役は
「しぶき」そのもの。おもちゃの種類・落とす高さ・投げ方によって、しぶきの
形がまったく変わるので、何度でも「もう1回！」と試したくなるように作って
あります。

## あそびかた

1. 画面下のボタンでおもちゃをえらぶ（🏓🎳🏖🥏🥤🧽🛟🍮）
2. 画面左のボタンで飛び込み台の高さをえらぶ（低・中・高）
3. 飛び込み台の上に浮かんでいるおもちゃを指でつかんで
4. そのまま指をはなす（ぽとん）か、勢いよくフリックする（ぽちゃーん！）

**つかんで、はなすだけ。** 台の高さとおもちゃの組み合わせで、飛沫の
大きさ・形・水中の泡のようすがぜんぶ変わります。

## 8つのおもちゃ

| おもちゃ | 絵文字 | 特徴 |
|---|---|---|
| ピンポンだま | 🏓 | 軽くてぷかぷか、しぶきは小さめ |
| おもいボール | 🎳 | ずっしり重く、深く沈んで力強いしぶき |
| ビーチボール | 🏖 | 大きくて軽い、ぼふんと広がるしぶき |
| えんばん | 🥏 | 平たく落ちると水面いっぱいに広がる、水面をなでるように入ると小さく飛沫が立つ |
| コップ | 🥤 | 上向き・下向きで空気の抱え方が変わる（下向きで落ちると泡がぶくぶく） |
| スポンジ | 🧽 | やわらかくてびちゃびちゃ、しぶきもふんわり |
| うきわ | 🛟 | 輪っかの形なので空気を少し抱え込み、ぷかぷか浮く |
| ゼリーボール | 🍮 | ぷるぷる揺れながら着水、はずむしぶき |

## 3つの飛び込み台

| 台 | 高さ |
|---|---|
| 低い台 | 2.2m |
| 中くらいの台 | 4.4m |
| 高い台 | 7.2m |

台が高いほど、おちる勢いが強くなり、しぶきも大きく・力強くなります。

## しぶきのルール（なぜそうなる？）

水しぶきは、いつも同じ見た目ではなく、次のような「わけ」に沿って変化します。

- **高いところから／重いおもちゃほど** → しぶきが大きく、力強くなる
- **平たい面から着水すると**（えんばんを寝かせて落とす、など）→ しぶきは
  横に広く低く広がり、水中のくぼみは浅い
- **とがった・まるい形できれいに刺さると** → しぶきは細く高いクラウン状に
  立ちのぼり、水中に深いくぼみができて、あとから勢いよく水柱が上がる
- **斜めに投げると** → しぶきは投げた方向に片寄って扇状に広がる
- **コップを口が下向きで落とすと** → 中に空気を抱え込んでいるので、
  着水したときに大きな「ぶくぶくっ」という泡がはじける（口が上向きだと
  ほとんど泡は出ない）
- **やわらかいおもちゃ（スポンジ・ゼリー）ほど** → しぶきはぷるぷる・
  びちゃびちゃした、まるみのある見た目になる

## ローカルでの起動方法

ビルド不要・依存パッケージ不要のプレーンな ES モジュール構成です。任意の
静的ファイルサーバーで配信するだけで動きます。

```bash
cd (このリポジトリのルート)
python3 -m http.server 8000
# ブラウザで http://localhost:8000 を開く
```

Python がなければ、`npx serve` や `php -S localhost:8000` など、静的
ファイルを返せるサーバーなら何でも構いません。

**対応環境**: iPhone / iPad の Safari を想定して作られています。縦向き
（ポートレート）・横向き（ランドスケープ）どちらでも遊べるようレイアウトが
調整されます。

## 技術概要

- **Three.js r170** を `vendor/three.module.js` としてリポジトリに同梱
  （`index.html` の importmap で `"three"` を解決）。ビルドステップなし、
  TypeScriptなし、外部npm依存なし。プレーンな ES モジュールのみ。
- **描画（しぶき: フォトリアル版）**: しぶき関連の描画は「グラブパス
  リフラクション」ハイブリッド構成に刷新（`src/watershading.js` +
  `src/main.js` の2パス描画 / `src/splash.js` / `src/droplets.js` /
  `src/underwater.js`）。
  - **グラブパスリフラクション**: 1フレームにつき最大2回描画（不透明な
    シーン→しぶき関連が何もなければそこで終了）。しぶきが発生している
    間だけ、①レイヤー0（通常シーン）を描画→②その描画結果をテクスチャに
    キャプチャ（`GrabPass`）→③しぶき専用レイヤー（`WATER_LAYER`）だけを
    クリアせずに重ね描画、という2パス構成。しぶき系マテリアルは共有
    GLSL チャンク（`WATER_GLSL` / `waterGlslCommon`）の `waterShade()` で
    フレネル反射・空サンプル・法線オフセットによる背景リフラクション・
    Beer-Lambert吸収による水の色づけ・太陽グリントを一括計算する。
  - **クラウン（王冠しぶき）**: 96×24分割の解析的な回転体メッシュ。
    立ち上がり→減速→リム肥厚→指状分裂（フィンガー）→落下、を頂点
    シェーダーで時間発展させ、フィンガー先端のちぎれで水滴を発生。
    厚み（薄いほど透明）を頂点属性として持たせ、フラグメントで
    フローノイズによる法線ゆらぎを加えてリフラクションが揺らめく。
  - **水滴インポスター**: `InstancedMesh` 1つでカメラ正面向きの
    球インポスターを描画（フラグメントでUVから球法線を再構成、円外は
    discard）。速度方向にプロレート形状で伸長、太陽グリントの疑似
    ブルームを追加。別の `InstancedMesh` でソフトな飛沫（ミスト）を
    非リフラクション・通常αブレンドで描画し、水滴の「白さ」を担当。
  - **水中ジェット（Worthington jet）**: なめらかなガラス質のチューブ
    メッシュ。上昇→自然なオーバーシュート→首のくびれ（ネッキング）→
    ピンチオフ（先端が1〜3個の衛星水滴として分離）→残った柱が沈んで
    消える、を時間発展させ、局所半径から厚みを算出してリフラクション/
    吸収に反映。
  - 描画コール数の目安: アイドル時 約22コール、3つのしぶきが重なる
    バーストでも 約40コール前後（予算 <80 コール以内）。しぶきが何も
    無いときは2パス目の描画自体をスキップ（`__lab.waterDebug()`で確認可）。
  - 上記に加え、水面シェーダー（フレネル風の輝き、最大12本の同時リング
    波紋）は変更なし。1粒ずつ Mesh を作るような重い実装は避けてある。
- **物理**: 自前実装の簡易物理エンジン（`src/physics.js`）。放物運動、
  水面での減速・浮力、跳ね返り、着水判定から `ImpactSpec`（着水点・速度・
  エネルギー・扁平度・斜め度・空気の抱え込み量など）を算出し、しぶき・
  水中エフェクト・カメラ・音のすべてがこの1つの値を参照して連動する
  設計（`docs/CONTRACTS.md` 参照）。
- **音**: サンプル音源を使わない、Web Audio API によるプロシージャル生成
  （`src/audio.js`）。
- **モジュール構成**: 環境・水面・上面しぶき・水中しぶき・おもちゃ・物理・
  入力・カメラ&音、それぞれ担当ファイルに分離（詳細は
  `docs/CONTRACTS.md`）。

### デバッグ用 API — `window.__lab`

自動テスト・QA用に、ページから直接おもちゃを操作できるデバッグ API を
`window.__lab` として公開しています（アプリの通常プレイには不要）。

```js
window.__lab.ready        // 初期化が終わると true になる
window.__lab.errors       // 実行時エラーを蓄積する配列（空が正常）
window.__lab.drop(toyId, platformId, vx, vy, vz, opts)
                           // 指定した台の先端からおもちゃを生成し、
                           // 指定速度で射出する。opts で rotX/rotY/rotZ
                           // （初期姿勢）や spin（初期角速度）も指定可能
window.__lab.state()      // { bodies, lastImpact, fps } を返す
window.__lab.heldScreenPos()
                           // 現在つかまれているおもちゃの画面座標(px)
window.__lab.renderInfo() // { calls, triangles } — そのフレーム全体
                           // （しぶきが2パス描画されるフレームは両パス
                           // 合算）の描画コール数スナップショット
window.__lab.waterDebug() // { pass2Active, dropletsAlive, sprayAlive }
                           // しぶき用2パス目が今フレーム実行されたか、
                           // 水滴/飛沫が生きているか（QA用）
```

例: `window.__lab.drop('cup', 'high', 0, 0, 0, { rotX: Math.PI })` で、
コップを口が下向きの姿勢のまま高い台からまっすぐ落とせます。

## 検証済み / 未検証

**検証済み（フォトリアルしぶき統合パス — 本パスで実施）**:

- R1（水シェーダー基盤/2パス描画）〜R4（水中ジェット）が並行実装した
  5ファイルを結合し、実際のゲーム内で通しプレイして検証。
  `src/splash.js` / `src/droplets.js` が動的 `import('./watershading.js')`
  で本物の共有シェーダーを使用していること（スタンドアロン用フォール
  バックに落ちていないこと）をランタイムで確認。`waterCtx.uniforms` は
  main が1回だけ生成した共有オブジェクトを splash/droplets/underwater
  すべてが参照しており、`uTimeW`/`uViewport`/`uSunDir` の毎フレーム更新が
  3モジュールへ伝播することを確認。
- **重大な統合バグを発見・修正**: `src/scene.js` の `scene.background` が
  単色 `THREE.Color` であるため、three.js の `WebGLBackground.render()`
  が `renderer.autoClear` の値に関係なく**強制的にフルクリア**する
  （`background.isColor` のとき `forceClear = true` になる仕様）。しぶき用
  2パス目の `renderer.render()` 呼び出しがこの強制クリアを踏んでしまい、
  1パス目で描いたプール・飛び込み台・水面が消え、しぶき（クラウン/
  ジェット/水滴）だけが背景色の上に浮いて見える不具合があった（しぶきが
  発生している間ずっと発生し、収まると自然に直る）。カメラ位置・レイヤー
  マスク・シャドウマップ・アンチエイリアス・グラブパスキャプチャ・
  別カメラインスタンスの使用など他の全変数をA/Bテストで切り分けて原因を
  特定。修正: 2パス目の描画直前だけ `scene.background` を一時的に `null`
  にし（`background===null` は強制クリアされない分岐）、描画後すぐ元の
  `Color` に戻す（`src/main.js`）。あわせて `__lab.renderInfo()` も
  `renderer.info.autoReset` が2回目の `render()` でリセットされるため
  1パス目のみの値しか返せていなかった問題を修正し、両パス合算の値を
  返すようにした。
- 上記修正後、ヘッドレスChromium上でスローモーション連続キャプチャ
  （heavyball/high、8フレーム）で目視確認: 背景（プールタイル・
  飛び込み台）がクラウンの壁・ジェット柱を通して明確に**屈折/歪んで**
  見える、リム（縁）のフレネル反射による明るさ、水滴の太陽グリント、
  チャンキーな水滴とは別レイヤーの白い飛沫（ミスト）、フィンガー
  （指状分裂）が時間とともに成長・分裂する様子、ジェットのくびれ→
  ピンチオフ（先端の水滴分離）まで、すべて目視で確認できた。
- 比較条件が引き続き因果的に区別できることを確認: heavyball vs disc
  （中段、`energy`/`flatness` が明確に異なる）、まっすぐ vs 斜め投げ
  （heavyball中段、vx=4 で `oblique` が 0→0.36 に変化）、低 vs 高
  （heavyball、`speed`/`energy` が単調に増加）。
- 決定性: heavyball/mid を2回リロードして再ドロップ、`seed` が完全一致
  （同じマクロ形状になることを確認）。
- フルスモークテスト: 8種トイすべてを中段台から順にドロップ（リロード
  はさみつつ）、全ケースでインパクト発火・エラーなし。コップを
  `rotX: Math.PI`（口が下向き）で高台から落とすと `cupTrap≈1` の泡が
  発生、ビーチボールは着水後もエラーなく浮上/リサーフェス。
- 入力回帰テスト: タップドロップ・フリック投げ・エイムアシスト・
  ミスグラブ耐性・トイ/台ボタン切り替え・リサイズ・連打の9項目すべて
  PASS（`scratchpad/input-verify.mjs`）。
- 描画パフォーマンス（修正後、両パス合算の正しい値）: アイドル時の
  描画コール数 約22回、3つのしぶきが重なるバーストのピークでも
  約38〜41回（予算<80コールを十分に下回る）。しぶきが何も無いときは
  `__lab.waterDebug().pass2Active` が `false` になり2パス目が実際に
  スキップされることを確認。fps はヘッドレスSwiftShaderで約15〜20
  （後述の通り実機性能の指標にはならない）。
- `window.__lab.errors` / コンソールエラー / ページエラー: 上記すべての
  シナリオを通じて0件。
- 全変更ファイル（`src/main.js` / `src/watershading.js` / `src/splash.js`
  / `src/droplets.js` / `src/underwater.js`）で `node --check` 構文チェック
  OK。デバッグ用に一時追加したグローバル・console.log は最終コミット前に
  すべて除去済み（`window.__lab` のみ）。

**未検証（本パスの対象外）**:

- 実機の iPhone / iPad（今回はすべてヘッドレス Chromium + SwiftShader
  ソフトウェアレンダリングでの検証）
- 実機でのタッチ操作の感触・ハプティクス（振動フィードバック）
- 実機でのフレームレート・GPU性能。ヘッドレスSwiftShaderの fps
  （アイドル時 約18fps、しぶきが重なる場面で約15fps）は**ソフトウェア
  レンダリングの数値であり実機のGPU性能を代表しない**。実機
  （特にiPhone/iPadのGPU）では大幅に高いfpsが期待できる。描画コール数・
  三角形数は実機性能に直結する指標として計測済み（上記参照）だが、
  実際のfpsは実機での確認が必要。
- **WebGL1 フォールバック経路（`NO_GRAB` 変種）**: `waterGlslCommon(false)`
  が生成する GLSL（`refractSample` が背景サンプルの代わりに単色の
  「深い水」フォールバックを返す変種）は、ブラウザ内で直接呼び出して
  文字列として正しく生成されること、`#define HAS_GRAB` が含まれないこと
  は確認した。また `src/main.js` が `renderer.capabilities.isWebGL2` が
  `false` の場合に `grabPass` を作らず `uSceneTex` が `null` のまま
  `sharedWaterUniforms(null)` を配ること、`splash.js`/`droplets.js`/
  `underwater.js` それぞれが `grabPass`/`uSceneTex` の欠如を検知して
  `hasGrab=false` の材質を選ぶことはコードレビューで確認した。ただし
  **実際にWebGL1コンテキスト（またはWebGL2でグラブパス無効）で描画させて
  見た目を確認する実機/実ブラウザテストは行っていない**
  （このヘッドレス環境の Chromium + SwiftShader は常にWebGL2を報告する
  ため、強制的にWebGL1相当にする手段がなく未検証）。

## 見つかった問題

以下は、フォトリアルしぶき統合パスより前の受け入れパスで見つかった軽微な
既知事項です（このセクション自体は当時のまま）。フォトリアルしぶき統合
パスで見つかった重大な統合バグ（`scene.background` 強制クリア問題）とその
修正は上の「検証済み / 未検証」内に記載しています。

- **同時オブジェクト数の一時的なオーバーシュート**: `src/physics.js` の
  `MAX_BODIES`（6）を超えると古いオブジェクトをフェードアウトさせて
  数を絞る仕組みがあるが、フェード対象は「静止中（floating/sunk）」の
  オブジェクトに限られる。12回連続投入のような高速連投では、まだ飛行中/
  着水直後のオブジェクトが多く、フェード候補が足りずに一時的に上限を
  超える（今回の計測では最大9個）。数秒後には6個まで戻り、無限に増え
  続けることはない。プレイ中に4歳児が連打しても致命的な破綻にはならない
  想定だが、余裕を持たせたい場合は `MAX_BODIES` を7〜8に上げる、または
  フェード対象の判定条件を緩める（例: 着水後一定時間が経過していれば
  flying中でもフェード対象にする）などの微調整が考えられる。
